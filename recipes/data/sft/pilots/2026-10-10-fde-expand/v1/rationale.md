What the material forced:

1. The agent is not a chatbot over free-form context; it is a spec-gated micro-agent. Its question, its tool surface and its legal answer vocabulary all come from frozen data (check_specs.py), and every answer passes one gate (shaping.py) that re-derives the vocabulary from the cause catalog, constrains the cause to the conclusion's family, clamps confidence, and demotes whole classes of reads (confirm-before-heal, absence margin, blocker coverage, fork attribution). So the harness description leads with that, and the evidence-to-answer rules are stated as rules the ANSWER must satisfy rather than as prose the agent might carry. RL/SFT data that violates them teaches answers the gate would reject.

2. The seeds are tool-call → observation training data, so payload fidelity is the main teaching signal. The source files document, in comments, several field incidents where a model misread a payload: available=false on a11y_search read as "the element is not there" (hence the reason string), a bare "unavailable" probe read as absence (hence reason + result enum), a comparison run over a single image that still answered "different page" (hence _missing_side). The harness section therefore gives the exact result shape for success, empty, unavailable and error PER TOOL, and several variations are built directly on those documented boundaries rather than on invented ones.

3. Variation design. Each variation changes one evidence fact a real run could produce (a slot not captured, a dialect not evaluable, a read that flips, an overlay that covers or clears, a page that is or is not the same) and then says what must be updated downstream — the calls, the observations, the answer. None of them names the outcome in the 'change' field; 'correct_when' states which outcome the harness rules make correct, so the generator derives the answer instead of being told it. Variation set composition: mostly ordinary mid-run realities (screenshots missing, tree missing, HAR missing — the seeds already show HAR absent), plus decision-boundary cases taken from rules and incidents the source documents: unverifiable vs no_match (record alias, D4/F29), generic-control lookalike on a sign-in page (the "never force found_in_place on a different page" rule), promo overlay vs A/B variant (RFC-043 catalog guidance), a session interstitial that only history can attribute, a keyboard that is present but not occluding, and an in-flow app dialog mistaken for a system blocker.

4. What I deliberately did NOT turn into a variation: anything whose correct answer the material does not determine. τ has no value in the source, so no variation hinges on the absence margin; crash-vs-restart adjudication does not ship crash evidence, so I left that ambiguity alone rather than inventing a preferred label; the catalog's supports/min_supports predicates appear in data but not in the gate, so I did not write a variation that requires them. Those are listed as unknowns in the harness description, per the instruction not to convert unknowns into rules.

5. Template. Instructions only, no output-format block, and the format-bearing literals (tool-call shape, result JSON) are avoided in favour of describing the contract, so the only brace slots are the six required ones. The rules are principles (keep the world; evidence drives outcome; reuse only valid calls/results; honour payload contracts; read evidence as your prompt reads it; end on the exact answer contract; keep the turn structure) rather than a long if-then list, and the variation is restated at the end with an explicit "nothing else changes" so the generator cannot quietly re-write the seed's world. obs_examples carries real results from other seeds so the generator can match the observation formatting (including the [obs:N] prefix, which the harness source does not explain and which I tag as inferred rather than asserting as a rule).
