## Job

Expand the seed into one new trajectory: the same micro-agent, the same situation, ONE assigned change. The seed is a real reviewed run — a user message carrying the failure context, assistant turns that call tools, tool turns that return observations, and a final assistant message that is the verdict JSON. Reproduce that shape with the change applied.

## Ground rules

1. Keep the world. Same platform, app or site, page, element, locator value, step ids, failure wording and the agent's voice. Never invent pages, elements, apps, causes or evidence sources. Every tool call uses a schema from <tool_schemas> and includes every field that schema declares — use "" as the wildcard value when the call does not constrain a field.

2. Evidence drives the run. After each observation ask: this agent has this question and this prompt — what does it do next, and what can it legitimately conclude from what it has seen so far? Never choose a conclusion and then invent evidence for it. If the seed's original answer no longer follows from the new evidence, the answer changes.

3. Reuse a seed call only when the call itself and the evidence behind its result both survive the change. When either is invalidated — the call no longer matches what is on screen, or the observation it reported no longer holds — replace it, and update every later call, observation and the final answer that depended on it. Never leave a stale observation beside contradicting evidence.

4. Stay inside the harness contracts. A tool result is exactly the JSON that tool returns for that outcome: no invented fields, no missing field the tool always emits, no reason sentence the tool would not write. A source that was not captured returns available false with a reason, never an empty list pretending to be an answer. a11y_search's no-match and no-tree-captured are different payloads. locator_probe's unverifiable and unavailable are not no_match. query_har's available false means no log was captured, not that nothing was pending. compare_screenshots returns the vision model's read as a STRING holding its own answer / confidence / observations JSON.

5. Read evidence the way <agent_system_prompt> reads it: programmatic before visual; a record-side probe says nothing about the live page; absence is heal-blocking and needs a screenshot that affirms the element's region is visible and the element is not in it; covered-with-no-source is occluded, not absent; an identity-family heal-enabling read and a blocker are hypotheses until the confirming check runs; a low confidence is honest, a guess is not.

6. Trajectory shape. Assistant turns carry tool_calls (a tool name plus an arguments object); tool turns carry that call's observation; the final assistant message is the answer JSON with no tool_calls. Keep the seed's call count, roughly — one more or one fewer if the change forces it. Never leave a tool call without its observation, or an observation without its call.

7. Every tool-turn content begins with an observation marker: `[obs:N] ` followed by the tool's JSON, where N starts at 1 and increments by one for each tool result in order — including error, unavailable and empty payloads. Never emit the raw JSON without the marker, and never reuse or skip an N.

8. Vocabulary is closed. The final message's conclusion and root_cause values may come only from <agent_system_prompt> — <assigned_variation> and <obs_examples> are not vocabulary sources, and a variation that names a term the prompt does not define must be answered with the prompt's closest valid term (e.g. the presence check's covered-target term is `occluded`, not a keyboard-specific conclusion). A key the prompt requires alongside a conclusion (page_kind when the conclusion is different_page) must appear in the JSON itself, not only in the detail sentence.

9. Cause naming. Name a specific root cause only when the evidence you generated positively supports that cause; when the run produced no positive evidence for one, or the change does not bear on causes, use root_cause null. The conclusion's contract comes from <agent_system_prompt>, never from a variation's prose.

10. Comparison reads. When a compare_screenshots kind compares two sides, the read's observations must describe each side present in the image set (recorded and live) or state that a side is missing — never collapse a comparison into a live-only description.

11. The final JSON has exactly the keys <agent_system_prompt> names, an honest confidence, and one short, non-hedged detail sentence naming evidence this run actually saw. No prose outside the JSON.

## Only this changes

The assigned change in <assigned_variation>, and nothing else. Everything else stays as in the seed: platform, app or site, page, element, locator, step ids and failure wording; the agent's question and its tool surface; the seed's wording style. Do not add a second change, do not soften or inflate the assigned one, and do not let the seed's original outcome survive if the new evidence does not support it.
